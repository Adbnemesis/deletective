# Security and privacy

## Implemented controls

- Guest credentials are 256-bit values generated by `crypto.getRandomValues`; only SHA-256 hashes are stored in the room.
- Room codes use eight random characters. Possessing a room code allows joining an available lobby, but does not grant host powers or an existing player's identity.
- WebSocket authentication happens in the first frame, never in a URL/query string. No room state is emitted before successful membership validation. Unauthenticated connections expire after five seconds.
- All game actions use the authenticated socket's player ID. User-supplied scores, author IDs, voter IDs and host flags have no authority.
- Start, settings, kick and rematch require host authorization. A host cannot change settings during a running round.
- Submissions and votes require the current round ID, correct phase, eligibility and server deadline. One locked answer, one vote, no self voting. Client retries cannot earn duplicate points.
- Private text is omitted from other clients' network state until lock/reveal. Anonymous author identities are omitted through competitive reveal/voting. Credentials never appear in public projections.
- HTTP bodies are capped at 4,096 characters; WebSocket frames at 2,048. Names, answers and reactions have explicit bounds. Inputs normalize Unicode/whitespace and strip control/direction characters. Markup and URL-shaped text are rejected.
- The default family setting applies a small language blocklist. All shipped prompts are curated family content. This filter is intentionally basic and can be evaded; it is not comprehensive moderation.
- Per-IP Durable Object counters limit room creation, joins, daily submission and connection upgrades. Each socket permits at most 35 frames per ten seconds; ten invalid commands close it. Max room members/pending sockets/history/lifetime joins are bounded.
- Mutations check browser Origin against the current/configured site origin; local development allows the documented localhost ports. Requests without Origin remain supported for non-browser clients, which still require room credentials for member actions.
- Temporary room state expires after 30 minutes inactivity or 2 hours maximum age. Expiry closes sockets and deletes content and alarms.
- Worker errors return generic messages; the application does not log request bodies, credentials, room codes or answers. Worker observability is off by default pending privacy review.
- Private room responses use `no-store` and `X-Robots-Tag: noindex, nofollow, noarchive`. Invite pages carry equivalent HTML metadata.

## Player controls

The host can remove players. Any player can leave. The interface supports local hiding/muting of another player's text and can notify the host about a reported answer. Reports are transient host notices; there is no offsite moderation team, permanent report database or automatic public publishing. A malicious participant can retain text they already saw; local hiding cannot erase another participant's device.

## Sharing and analytics

Answers are private to the session unless a player explicitly invokes a share/download action. Share text/images must exclude room credentials and invite codes. A downloaded fictional chat is clearly branded as a game. Daily completion and preference storage remain in the browser. Analytics integrations must never receive answer content, names, credentials or private room URLs; live analytics/search accounts require owner setup.

## Deployment requirements and limits

Use HTTPS/WSS in production. Keep Cloudflare access tokens outside the repository. Configure the approved site origin and verify security headers on the deployed asset route and room route. Astro emits a document CSP with build-time hashes for its trusted inline scripts and disables inline script attributes. The base response policy permits hydration-compatible inline scripts, while the stricter document policy narrows execution to the generated hashes. Inline style attributes remain permitted for React presentation. Passing browser tests observed no CSP refusals; this is not an independent security audit. Player text must continue to use escaped React text nodes, never `dangerouslySetInnerHTML` or HTML template concatenation.

This is unlisted invitation-based multiplayer, not cryptographic end-to-end encryption. Cloudflare processes transport and temporary room state. SHA-256 IP-derived abuse keys expire after one minute, but they are pseudonymous while present. Cloudflare can retain operational request metadata according to account/provider settings. Browser storage is accessible to scripts running in the same origin and can be cleared by the player. Shared-screen users can see content on that screen.

Known limitations: no sophisticated hate-speech classifier, no human moderation queue, no distributed attack guarantee, no prevention of invite re-sharing, no independent penetration test and no proof that all browser extensions are safe. Same-origin script compromise would compromise the current player's session. Deploy first to staging and validate quotas, production Origin handling, headers, reconnect/hibernation, and cleanup before launch.
